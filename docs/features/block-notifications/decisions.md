# Avisos de Fin de Bloque — Decisiones de Diseño

> Registro de las decisiones del issue [#138](https://github.com/EmanuelAngel/pomody/issues/138), cerradas con el usuario **antes** de escribir la primera línea.
> Este documento explica **por qué** cada cosa es como es, y qué se descartó en el camino.
>
> El **qué** está en [`spec.md`](./spec.md). Precedentes: [`distraction-detector/decisions.md`](../distraction-detector/decisions.md) (canal del SO y permisos), [`mini-player/decisions.md`](../mini-player/decisions.md) (ventana siempre-arriba).

---

## 1. Objetivo

Que el usuario se entere de que un bloque terminó **incluso cuando no está mirando la ventana**, y que al volver encuentre el aviso todavía ahí. Nada más: el aviso informa, no opera el timer.

## 2. Decisiones

| Decisión                       | Valor                                                                                           | Por qué                                                                                                                                                                                                                                                       |
| ------------------------------ | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Canal                          | **Híbrido**: notificación del SO en desktop + toast in-app en todas las plataformas             | El SO es el único canal que llega a otra ventana; el toast es el único que sobrevive hasta que el usuario vuelve. Uno solo de los dos deja la mitad del issue sin resolver.                                                                                   |
| Notification API del navegador | **Descartada**                                                                                  | Suma un prompt de permiso del navegador y un segundo adaptador con sus degradaciones, para un caso (pestaña en segundo plano) que el toast ya cubre al volver.                                                                                                |
| Cuándo dispara                 | **Solo si la ventana está oculta o sin foco** (`visibilityState === 'hidden' \|\| !hasFocus()`) | Con la ventana enfocada el cambio de fase ya se ve y suena; un aviso encima duplica el estímulo. El predicado cubre pestaña oculta, ventana minimizada y ventana tapada por otra app.                                                                         |
| Excepción siempre-arriba       | **No avisa con `windowState.isAlwaysOnTop`** (Mini-Player)                                      | El Mini-Player flota siempre visible: el cambio de fase está en pantalla por diseño. Avisar ahí sería tapar la propia razón de existir de la ventana compacta.                                                                                                |
| Skip / reset                   | **No avisan**                                                                                   | El FSM emite `block-skipped` para el skip y no emite evento en el reset: el usuario está frente a la app eligiendo la fase siguiente.                                                                                                                         |
| Ajuste                         | **Switch propio en Behavior, ON por defecto, independiente de `soundEnabled`**                  | Es la sección que ya reúne sonido, revitalización y detector. ON por defecto porque el issue parte de que el usuario quiere enterarse; independiente porque apagar el audio no debe apagar el canal visual.                                                   |
| Permiso del SO                 | **Se pide al encender el switch; la negativa lo devuelve a off con una línea que lo explica**   | El estado nunca miente sobre lo que va a entregar. Pedirlo en el primer fin de bloque haría que el primer aviso se pierda sin explicación.                                                                                                                    |
| Movimiento del switch          | **Optimista y reversible**                                                                      | El thumb responde al click y vuelve si el SO niega. Esperar la respuesta antes de moverlo deja la UI congelada en el gesto más común de la feature. Con `checked` bindable, un rechazo sin cambio de prop deja el thumb mintiendo.                            |
| Copy                           | **Título = fase completada; cuerpo = fase siguiente**, resuelto por `calculateNextCycleStep`    | El aviso dice qué pasó y qué viene. Reimplementar el ciclo en el copy habría creado una segunda autoridad sobre los rounds.                                                                                                                                   |
| Botones en el aviso del SO     | **Ninguno**                                                                                     | En Windows los botones pueden no renderizarse (`distraction-detector/decisions.md` §5.2). Prometer acciones que a veces no existen es peor que un aviso que solo informa.                                                                                     |
| Click en el aviso              | **Enfoca la ventana** (`onAction` → `tap` → `setFocus`)                                         | Un aviso es un puntero de vuelta a la app. Degradación documentada: en Windows el click solo se reporta mientras el toast está en pantalla; una vez en el Centro de actividades no llega el evento.                                                           |
| Toast                          | **`sonner` de shadcn-svelte, persistente hasta el próximo bloque, informativo sin acción**      | Regla 3 de `AGENTS.md`: la UI se compone con shadcn-svelte, no a mano. Persistente porque el aviso nace cuando el usuario no mira: auto-descartarlo lo borra antes de que vuelva. Sin acción por decisión de producto: el usuario aprieta play donde siempre. |
| Dónde vive la lógica           | **`block-notice.svelte.ts`, no `timer.svelte.ts`**                                              | Precedente `DistractionState`: se suscribe a `timerState.onEvent`, posee su ajuste y compone los puertos. El estado del timer ya carga FSM, persistencia y ticker; no necesita además permiso del SO, foco y copy.                                            |
| Predicados                     | **Inyectados** (`isWindowUnattended`, `isAlwaysOnTop`)                                          | Los tests de estado corren en Node: tocar `document` ahí obligaría a stubs de DOM y volvería frágil la regla más importante.                                                                                                                                  |
| Nombres de archivo             | **kebab-case en todo archivo nuevo**                                                            | Regla del repo; `distractionState.svelte.ts` y `windowState.svelte.ts` quedan como están (rebeldes conocidos, no se renombran en esta feature).                                                                                                               |
| Entrega                        | **Dos PRs encadenados**: (1) canal del SO, (2) toast in-app                                     | El PR 1 cierra el caso central del issue y se revisa solo; el PR 2 suma la superficie in-app con sus tests de browser.                                                                                                                                        |

### 2.1. Cierre del toast

| Decisión                  | Valor                                                      | Por qué                                                                                                                                                                                                                                                         |
| ------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Duración del toast        | **`Infinity`, sin auto-descarte**                          | Es el registro de que el bloque terminó. Vive hasta que el usuario inicia el bloque siguiente, resetea, salta o lo cierra con la X.                                                                                                                             |
| Cierre del toast          | **Una sola condición: el timer deja de estar `completed`** | Cubre las tres salidas reales (start, reset, skip) con una regla, y usa la suscripción al snapshot en vez de adivinar desde los eventos: `start` y `reset` no emiten evento de dominio.                                                                         |
| Host del toast            | **Shell principal, no la rama Mini-Player**                | El Mini-Player ya está suprimido por el predicado; montar el host ahí sería un canal que nunca se usa.                                                                                                                                                          |
| `mode-watcher` del vendor | **Eliminado; el layout pasa el hint `light`/`dark`**       | El CLI de shadcn instala el toast importando `mode-watcher`, que no conoce los tres temas Rosé Pine (`dark`, `dawn`, `oled`). Una dependencia que adivina el tema por el SO y contradice a `themeState` es bloat que miente; la orientación la decide el shell. |

## 3. Deuda y límites aceptados

- El permiso se pide al encender el switch. Una instalación nueva, con el default ON, deja el primer pedido al adaptador en el primer fin de bloque; en Windows ese pedido no abre diálogo.
- El aviso del SO no se puede verificar en E2E. La garantía es el doble del cliente nativo en el adaptador más el estado que decide llamarlo.
- El toast y el aviso del SO no se deduplican entre sí: con la ventana oculta se emiten los dos, y el toast es lo que el usuario encuentra al volver.
